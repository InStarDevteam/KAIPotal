## 1. 시스템 아키텍처 개요

### 1.1 현재 구현 아키텍처 (데모/PoC 배포 기준)

```
[브라우저]
   │ HTTPS
   ▼
[Firebase Hosting]  ← 정적 React 앱 (Backstage 프론트엔드 빌드 산출물)
   │ /api/** rewrite
   ▼
[Cloud Run: Backstage Backend (Node.js/Express, 포트 7007)]
   ├─ 커스텀 포털 BFF 플러그인: /api/portal/v1/* (15개 라우터, 20개 서비스)
   ├─ Backstage 표준 플러그인: catalog, auth(OIDC/guest), scaffolder, techdocs,
   │   search, kubernetes, notifications, signals, permission, mcp-actions
   ▼
[Cloud SQL PostgreSQL]  (portal_business DB, portal 스키마, 12개 마이그레이션)

[로컬 개발용 Docker Compose 인프라 — 데모 배포 미포함]
   ├─ Keycloak 26.2.4 (OIDC SSO, realm: kt-ai)
   ├─ OpenSearch 2.19.1 + Dashboards (통합검색)
   ├─ OpenMetadata 1.6.0 (데이터/AI 메타데이터 카탈로그)
   └─ PostgreSQL 16 (로컬 통합시험용)
```

- 근거: `kt-ai-portal/docs/ARCHITECTURE.md`, `firebase.json` (Hosting→Cloud Run rewrite), `cloudbuild.yaml`, `backstage-portal/packages/backend/src/index.ts`

### 1.2 목표(운영) 아키텍처 — 내부 설계 문서 기준

- 폐쇄망·VM 설치를 최종 기준으로 가정 (인터넷 차단, 내부 CA 기반 TLS, 망분리 DMZ/업무망/관리망) — `docs/VM_INFRASTRUCTURE_DESIGN.md`
- 3중화: WEB/Kong/BFF 3대 분산, PostgreSQL Primary 1 + Standby 2 (Patroni + etcd), Keycloak 3대 + HA DB, OpenSearch 3노드 — `prompt/KAIPotal_Implementation_Test_Spec.md` §8
- API Gateway: Kong DB-less 3노드
- 플랫폼 연계 경계: 포털은 신청/승인/조회/오케스트레이션만 담당, 실제 학습·자원 생성은 데이터 플랫폼/AI 플랫폼/지능형 클라우드(CMP) 책임

### 1.3 디렉토리 구조

| 디렉토리 | 역할 |
|---|---|
| `backstage-portal/` | Backstage 모노레포 (Yarn 4 workspaces: `packages/app` 프론트엔드, `packages/backend` 백엔드). 커스텀 기능은 프론트 26개 모듈 + 백엔드 `modules/portal/` BFF로 구현 |
| `docs/` | 아키텍처, 요구사항 추적표(SFR-001~021, 기능 163개), 설계·QA·배포 문서 80여 건 |

| `notes/` | 기술기준(REQUIREMENTS.md), 기술 결정사항(DECISIONS.md) |
| `proposal-package/` | 제안서·PPT·견적서 산출물 |

### 2.6 AI / LLM 관련

- **실제 LLM·벡터검색·임베딩 파이프라인 미구현**: LangChain, OpenAI SDK, 벡터DB 클라이언트 등이 코드베이스에 없음 (전수 검색 확인)
- 유일한 AI 인접 기능: Backstage MCP Actions 플러그인 (MCP 클라이언트가 포털 기능을 도구로 호출)
- 의미기반 검색(벡터 인덱스): "검색 엔진 미선정"으로 명시적 미구현 처리
- OpenSearch는 키워드 검색(multi_match)만 사용. 한글 analyzer 적용 설계
- 설계 방침: "포털에 LLM 실행 기능을 추가하지 않음" — 학습·추론 엔진은 AI 플랫폼 책임, 포털은 카탈로그/연계 표시

## 4. 주요 리스크 및 개발팀 확인 요청사항

### 4.1 최우선 확인 (P0)

1. **원본 RFP(최종공고문 260723_v1) 확보**: 현재 확보 자료는 FP 견적 산정표뿐이며, 전자정부프레임워크·Java·GS인증 등 기술 강제 조항의 존재 여부를 확인할 수 없습니다. 원본 확보가 모든 검수 대비의 선행 조건입니다.
2. **전자정부프레임워크/Java 의무 여부**: 만약 의무가 있다면 현재 Backstage(Node.js/React) 구현과 정면 배치됩니다. 이 경우 선택지는:
   - (가) 실 구축 시 전자정부프레임워크(Spring Boot) 기반으로 재구축하고 현 PoC는 "기능 시연용 프로토타입"으로 포지셔닝
   - (나) 제안서 단계에서 Backstage 채택의 타당성(오픈소스 개발자 포털 표준, 플러그인 생태계, 카탈로그 중심 설계의 요구사항 부합성)을 소명하고 언어 자유 규정 확인
   - ※ 어느 쪽이든 발주처 사전 협의 없이 진행하면 검수 리스크가 큽니다.

### 4.2 아키텍처 개선 요청 (P1)

3. **폐쇄망 전환 계획 구체화**: Firebase Hosting/Auth, Cloud Run, Cloud SQL → 내부 웹서버+Kong+PG(Patroni)+Keycloak 전환 시 변경 범위 산정 및 전환 리허설 필요.
4. **오프라인 설치 산출물**: SBOM, npm mirror/OCI registry 기반 오프라인 설치 패키지, 라이선스 목록 문서화.
5. **MPKI 인증서 로그인**: Keycloak X.509 인증 플로우 설계 및 PoC.
6. **MFA·로그인 정책 enforcement**: 환경설정에 저장된 정책이 실제 인증 흐름에 적용되는지 end-to-end 검증.
7. **의미기반 검색**: 요구(SFR-015 "유사 명칭/의미 기반 검색")에 대해 벡터 검색 엔진 선정 필요 (현재 명시적 미구현).

### 4.3 문서·증적 보완 (P2)

8. 요구사항 추적표(RTM)에 "원본 RFP 조항 번호" 컬럼 추가 (현재는 SFR/기능번호 기준).
9. 로그 보존 기간 등 K-RMF 관련 설정값은 기관 기준판 확정 후 반영 (임의 설정 금지 — Test Spec L250).
10. 성능 목표(동시 300~500명)는 설계 가정이므로 발주처 확정 기준 확보 및 부하시험 계획 수립.

## 5. 결론

- 현재 구현은 **Backstage 1.52 + React 18 + TypeScript + Node.js + PostgreSQL + Keycloak + OpenSearch** 스택의 잘 구조화된 포털 PoC이며, SFR-001~021 기능 요구사항 대비 대부분 "부분 충족" 수준(화면·BFF·DB 설계 구현, 실 플랫폼·실 인증 연동 미완)입니다.
- 기술스택 자체는 확보된 요구사항 자료와 충돌하지 않으나, **확보 자료가 FP 산정표에 국한**되어 있어 전자정부프레임워크/Java/GS인증 등 국방·공공사업에서 통상 등장하는 기술 강제 조항의 존재 여부가 불명확합니다. 이것이 검수의 최대 리스크입니다.
- 개발팀에는 §4의 확인 요청사항을 전달하고, 특히 4.1-2(언어/프레임워크 의무)에 대한 발주처 확인 결과에 따라 후속 전략을 결정해야 합니다.
