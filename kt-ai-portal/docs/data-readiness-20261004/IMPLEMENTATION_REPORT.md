## 1. Firebase와 PostgreSQL의 현재 구성

현재 프로젝트는 **Firebase Hosting → Cloud Run의 Backstage/BFF → Cloud SQL for PostgreSQL 18.6** 구조다. `/api/**`는 Hosting에서 Cloud Run으로 전달하며, 업무 데이터는 Cloud SQL의 `portal` 스키마에 저장한다. 화면에 하드코딩한 목록으로 실제 원장을 대체하지 않는다.

Firebase의 관계형 서비스 [SQL Connect](https://firebase.google.com/docs/sql-connect)는 Cloud SQL PostgreSQL 기반이며, 과거 Data Connect라는 이름으로 제공되었다. 이 프로젝트의 현재 백엔드는 이미 Cloud SQL에 연결되어 있으므로 별도 PostgreSQL을 새로 만들거나 SQL Connect 방식으로 API를 전환하지 않고 기존 DB를 사용했다. Firestore나 Realtime Database를 PostgreSQL로 취급하지 않는다.

## 2. 국방 MDR 연계를 준비하는 영속 사전

기관의 공식 표준단어·용어·도메인·코드 원본과 등록 규칙은 아직 수령하지 않았다. 따라서 원천은 `project_draft`, 매핑은 `provisional`로 저장하고 공식 기관 ID는 NULL로 유지한다. 임시 ID를 기관 승인 ID처럼 사용하지 않는다. 실제 스키마를 기준으로 등록하여 기관 원본을 받을 때 출처·버전·항목별 대응을 검토할 수 있게 했다.

| 신규 테이블 | 역할 | 운영 적재 행 수 |
|---|---|---:|
| `fc_metadata_releases` | 사전 버전, 원천 URI·SHA-256, 적재 시각, 테이블/컬럼 수, 기관 원본 상태 | 1 |
| `fc_metadata_domains` | 프로젝트 임시 도메인과 실제 PostgreSQL 기술 도메인 | 22 |
| `fc_metadata_words` | 임시 표준단어, 영문명·약어·정의 | 96 |
| `fc_metadata_terms` | 임시 용어와 단어 구성, 컬럼별 논리 용어 | 606 |
| `fc_metadata_codes` | 실제 CHECK에 대응하는 코드그룹·값·한글명·적용 컬럼 | 161 |
| `fc_metadata_columns` | 스키마·테이블·컬럼, 자료형·NULL·PK·기본값·FK/CHECK, 개인정보·보존 분류, 사전 대응 | 548 |
| **합계** | 신규 기술 메타데이터 원장 | **1,434** |

기존 CSV의 임시 도메인은 14개이며 실제 PostgreSQL 기술 도메인 8개를 함께 저장해 영속 사전은 22개다. 기존 용어 58개에 컬럼별 임시 용어 548개를 추가해 606개다. 이 숫자는 공식 국방 표준 용어 수나 승인된 기관 코드 수를 의미하지 않는다. 기관 ID·버전·출처의 미수령 상태는 [실제 적재 결과](evidence/dictionary-import.json)와 [운영 사전 확인](evidence/database-after.json)에 기록했다.

사전은 관리자용 **개발 관리자 → 포털 데이터 사전**에서 테이블·컬럼·한글명으로 검색하고 페이지를 이동해 조회한다. 현재 페이지 CSV 내려받기를 제공한다. `integration.view` 권한이 필요하며, 일반 사용자·유효하지 않은 테넌트·미인증 요청은 서버에서 거부한다. 사전 테이블은 업무 개인정보 값을 저장하는 장소가 아니라 구조·논리 정의를 관리하는 장소다.

사전 생성·적재에는 다음 검사를 적용했다.

- CSV와 실제 DB의 테이블/컬럼 목록, 자료형·NULL·PK·기본값·numeric 정밀도·FK를 대조한다. 누락·중복·불일치는 적재 전에 실패한다.
- 코드 값은 실제 PostgreSQL CHECK와 비교한다. 없는 코드·빠진 코드·중복 코드 및 정의되지 않은 구성 단어는 거부한다.
- 사전 버전과 원천 해시를 저장한다. 같은 버전·같은 원천의 재실행은 추가 행 없이 반환하고, 같은 버전의 다른 원천은 거부한다.
- 컬럼의 사전 버전·도메인·용어 참조는 FK로 연결한다. 런타임은 사전 6개 테이블에 SELECT만 가능하며 INSERT/UPDATE/DELETE/TRUNCATE는 허용하지 않는다.
- 사용자 프로필 JSON을 개인정보로 분류했다. 해병대·내부 코드명 오타를 수정했다. 개인정보·보존 분류 역시 기관 확정 전의 임시 기준이다.

CSV 산출물: [데이터 사전](data/DATA_DICTIONARY.csv), [단어](data/STANDARD_WORDS.csv), [용어](data/STANDARD_TERMS.csv), [도메인](data/STANDARD_DOMAINS.csv), [코드](data/STANDARD_CODES.csv), [기관 대응 대기 목록](data/MDR_MAPPING.csv). 9월 29일의 48테이블/485컬럼·637건 검증 자료는 당시 이력으로 보존하고 이번 결과로 재사용하지 않는다.

## 3. 실제 DB에 추가한 업무 샘플

기존 **국방부 공통** 테넌트와 이미 승인된 협의 사용자·멤버십만 사용하여 **25개 기존 업무 테이블에 74행**을 추가했다. 실제 적재를 기록하는 `sample.import` 감사 이벤트 1행을 함께 추가했다. 기존 사용자·외부 신원·소속·역할·권한·프로필·플랫폼 접근 정책·개인 선호·테넌트 브랜드를 새로 만들거나 덮어쓰지 않았다.

명칭·제목·설명에는 `[시연 샘플]`을 표기했다. 실제 군번·실인물·작전·장비 데이터는 추가하지 않았다. 새 조직·그룹 노드는 `SAMPLE-` 코드의 부모·자식 계층이며 실제 사용자 소속이나 권한을 배정하지 않았다. 별도 실증 사업 관리 프로그램이나 요구하지 않은 과제 기능은 추가하지 않았다.

샘플 프로젝트 계정의 거래는 `100,000 + 25,000 − 18,000 + 1,000 = 108,000 C`이며 현재 잔액과 일치한다. `3,000 × 6 = 18,000` 차감 단가·수량도 대조했다. 이는 합성 프로젝트의 시연값이며 실제 계약단가·계량·과금은 아니다. 상세 테이블별 계획은 [샘플 설계](../sample-data-20261004/SEED_DESIGN.md)에 있다.

시드는 기본 dry-run이며 명시적 apply에서만 한 트랜잭션으로 INSERT한다. 동일 테넌트·batch의 결정적 ID와 advisory lock을 사용한다. 재실행은 **추가 업무행 0·추가 감사 0**이었다. 사용자가 시연 후 바꾼 제목·상태·버전·잔액을 자동 초기화하지 않는다. 자연키/소유자 충돌·타 테넌트 부모·JSON 참조 불일치·부분 손상된 크레딧 원장은 수정 없이 거부한다.

운영 증적: [적재 전 계획](../sample-data-20261004/evidence/sample-seed-plan.json), [실제 74행 적재](../sample-data-20261004/evidence/sample-seed-applied.json), [재실행 0행](../sample-data-20261004/evidence/sample-seed-repeated.json), [적재 후 관계·잔액·테이블 조회](evidence/database-after.json).

55개 업무·기술 테이블을 모두 조사해 **업무 샘플 25·기존 실데이터 10·기술 사전 6·미적재 사유가 있는 원장 14**로 분류했다. 전체 목록과 적재 전후 행수·빈 원장 사유는 [55테이블 커버리지](../sample-data-20261004/SAMPLE_TABLE_COVERAGE.md)와 [CSV 목록](../sample-data-20261004/SAMPLE_TABLE_COVERAGE.csv)에 있다. 파일 원장·외부 outbox는 실제 저장/실행 계약이 필요하고, 초대·공감·그룹 소속·권한 위임·개인 선호·설정 이력은 실제 대상이나 사용자 행동으로 생성한다. 기본 정책으로 동작하는 빈 테이블을 임의 설정값으로 채우지 않는다.

## 4. 기능 전수 조사에서 바로 고친 사항

앱 라우트와 실제 BFF의 조회·등록·수정·승인·권한 경로, 서버 모드의 하위 기능을 대조했다. 화면별 현재 동작과 연동 경계는 [기능 전수 점검표](../sample-data-20261004/FEATURE_AUDIT.md)에 정리했다. 기존 홈 디자인 4종, 플랫폼 4개 진입, 권한별 포털 업무 첫 화면, 기존 메뉴·기능을 유지한다.

| 발견한 문제 | 보완한 결과·검증 |
|---|---|
| textarea의 줄바꿈·들여쓰기가 서버에서 422 | 프로젝트/제안/검토/카탈로그 장문에 CR/LF/TAB 허용. 제목·이름은 단일행을 유지하고 태그·금지 제어문자는 거부 |

| 내 제안·내 공감·상태/분류 수치가 제한된 목록에서 계산 | 서버에서 현재 권한으로 보이는 전체와 실제 본인 공감을 집계. 필터 후 페이지 적용 |
| 승인자가 소속 전체 신청을 보는 화면이 ‘내 신청’으로 표시 | 본인은 내 신청, 승인자는 신청·승인 이력/전체 신청으로 실제 조회 범위를 안내 |

## 6. 백업·보존·복귀

신규 migration과 샘플을 넣기 전에 운영 `portal` 스키마를 백업했다. 백업 원본은 저장소 밖에 파일 권한 600으로 보관하며, 보고서에는 비밀번호·토큰·백업 데이터 내용을 포함하지 않는다. 실제 로컬 PostgreSQL 18.6에 복원해 테이블 51개와 migration 11개, 적재 전 테이블별 모든 행수가 일치하는 것을 확인했다. 백업을 만들기만 한 것이 아니라 복원까지 수행했다.

적재 후 기존 신원·소속·권한·프로필·접근 정책 등 보호 대상 15개 테이블의 행수가 모두 보존되었고, 샘플 25개 테이블의 적재 전 행수+계획 INSERT가 사후 행수와 일치했다. 74개 샘플의 PK·부모/테넌트/사용자·JSON 참조 및 크레딧 잔액/거래합계를 대조했고 DB FK 68개 모두 VALIDATED였다. 운영 전후 증적의 보호 확인은 **행수 기준**이며 필드별 원문 snapshot은 포함하지 않는다. 기존 값 보존은 INSERT 전용 적재 코드와 실제 일회성 시험의 필드값 보존 검사도 함께 확인했다.

DB 변경은 사전 6테이블 추가와 합성 업무행 INSERT다. 기존 컬럼·키·상태 코드를 삭제하거나 기존 업무행을 UPDATE/DELETE하지 않았다. 실패한 적재는 트랜잭션으로 rollback한다. 이미 사용자가 샘플을 수정하거나 승인한 뒤 자동 삭제·원장 재초기화를 하지 않는다.

화면/백엔드 장애는 검증된 이전 Hosting release·Cloud Run revision으로 전환한다. 이전 공개 기준은 [10월 3일 배포 보고서](../requirements-review-20261003/RELEASE_REPORT.md)의 Cloud Run `kt-ai-portal-demo-requirements-20261003-r3`, Hosting `e9d512ba60d828c3`이다. 신규 사전의 파괴적 down migration을 서비스 복귀 수단으로 사용하지 않는다. DB 복구가 필요하면 이후 고객 작업·감사·외부 참조를 함께 검토한 별도 복구 절차로 수행한다.
