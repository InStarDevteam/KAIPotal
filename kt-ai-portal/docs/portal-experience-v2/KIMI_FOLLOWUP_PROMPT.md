# Kimi Code 후속 개발 프롬프트

다음 내용을 그대로 전달하세요.

---

현재 저장소 `kt-ai-portal`의 미커밋 변경을 보존한 상태에서 후속 개발하라. 먼저 `docs/FINAL_RFP_PORTAL_BOUNDARY_REVIEW.md`, `docs/portal-experience-v2/DESIGN_REVIEW.md`, `ROLE_LANDING_MATRIX.md`, `VALIDATION.md`, 기존 `docs/portal-experience/IMPLEMENTATION.md` 및 저장소의 최신 RFP/제안서 자료를 읽어라.

완성된 구조:
- 메인 Aurora/Focus/Orbit/Canvas 4종, 로그인 시안 선택, 앱 아이콘 런처.
- 포털 업무 버튼은 `/portal-work`로 직접 이동. 유효 권한에 따라 개인·프로젝트·테넌트·포털운영·보안·감사 첫 화면을 선택한다.
- 기존 업무 기능과 권한을 재사용하며 대시보드가 새 승인 권한을 만들지 않는다.
- 데모에서는 기존 로컬 저장소와 소속별 샘플을 읽고 운영 모드에서는 미연동 수치를 표시하지 않는다.

우선 개발할 내용:
1. 기존 백엔드 데이터 모델/API를 조사한 뒤 실제 업무 첫 화면 집계 연동을 구현하라. 중복 API를 만들지 말고, 필요한 추가 집계 계약은 기존 40개 플랫폼 연계 계약과 관계를 명시하라. 현재 사용자 프로젝트 멤버십, 내 신청, 승인 가능한 범위, 프로젝트 크레딧, 자원 사용량, 감사 최근 기록이 대상이다.
2. 프로젝트 멤버십과 테넌트별 공유 승인함을 서버에서 검증하라. 로컬의 같은 테넌트 샘플 프로젝트를 실제 ‘내 프로젝트’로 간주하지 말라. 다른 사용자가 제출한 신청이 적절한 관리자에게 보이는 흐름, 승인 후 동시 갱신과 이력 기록을 구현하라. 승인 권한은 기존 정책을 기준으로 하며 정책 변경이 필요하면 근거를 분리해 제시하라.
3. API 실패·부분 실패·지연·빈 목록·만료·권한 없음·테넌트 전환 중 오래된 응답을 구분하라. 실제 모니터링의 관측 시각, 수집 주기, 지연 상태를 표시하라. 실패 시 샘플 성공으로 대체하지 말라.
4. 실제 플랫폼 연결은 기존 개발 관리자 화면을 사용해 계약·엔드포인트·인증·타임아웃·허용 호스트를 확인하고 테스트하라. 서버 측 SSRF 방어, RLS, 감사 원자성을 유지하라. 프런트엔드에 시크릿을 넣지 말라.
5. 고객이 선택한 디자인이 확정되기 전에는 4종과 비교 화면을 유지하라. 확정 후 `designReviewEnabled` 및 로그인 4개 버튼 제거 작업을 별도 변경으로 처리하라. 기존 계정·테넌트 개인화와 메뉴 순서를 보존하라.

범위 제한:
- 기능을 임의로 삭제하거나 RFP 외 기능을 확장하지 말 것. AI 학습·데이터 가공·클라우드 프로비저닝·VDI 세션 상세 기능은 각 플랫폼에서 수행한다.
- UI에 요구사항 ID를 복원하지 말 것. 내부 추적 문서는 보존한다.
- 이미 보류된 K-RMF 전용 메뉴는 별도 요청 없이 복원하지 말 것.
- 데모 인증을 제로트러스트 구현 완료로 보고하지 말 것. 실제 IdP/MFA/단말 정책과 SSO는 확정된 기관 연동 조건에 따른다.

검증:
- `tsc:full`, 프런트엔드·백엔드 단위 테스트, 앱 lint, 로컬 PostgreSQL runtime 검사.
- `scripts/test-portal-experience-v2.mjs`, 기존 포털/테넌트/개발 콘솔 브라우저 검증.
- 6개 역할, 복수 역할, 5개 테넌트, 숨긴 메뉴, 접근 제한, 모바일/데스크톱, 새로고침·뒤로가기, 승인 동시성 및 교차 테넌트 차단을 확인할 것.
- 운영 배포 여부와 로컬 검증 범위를 명확히 구분해 변경 파일·API 계약·테스트 결과·미완료 항목을 한국어로 보고하라.
