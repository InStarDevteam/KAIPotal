# Kimi Code 후속 개발 지시문

작성 기준: 2026-09-24. 아래 내용을 Kimi Code에 전달한다. 이 문서는 개발 지시문이며, 나열된 후속 기능의 구현 완료 보고가 아니다.

---

KAIPotal의 기존 기능과 2026-09-24 포털 경험 개선을 보존하면서 운영 연계를 완성해 주세요. 저장소는 `kt-ai-portal`이며 앱은 `backstage-portal` 아래에 있습니다. 먼저 작업 트리와 최신 소스를 확인하고, 미커밋 변경을 덮어쓰거나 이미 구현된 기능을 다시 만들지 마세요.

## 1. 반드시 유지할 제품 방향

- 로그인 이후 첫 화면은 AI 플랫폼, 데이터 플랫폼, 클라우드 플랫폼, VDI 진입에 집중합니다. 첫 화면에 사이드바, 상세 통계, 업무 테이블을 다시 채우지 마세요.
- 상단 앱 아이콘 메뉴에서 네 플랫폼과 포털 내부 업무 기능에 접근할 수 있어야 합니다. 프로젝트/워크스페이스, 검색, 카탈로그, 반입·반출, 크레딧, 제안 게시판, 내 계정과 관리 기능의 기존 URL·권한·역할을 유지하세요.
- 네 가지 메인 화면 시안과 로그인 진입 선택은 고객 협의를 위한 임시 기능입니다. 최종안이 확정되기 전에는 임의로 하나를 삭제하거나 기본 화면을 바꾸지 마세요. 확정 후에는 설정으로 선택기를 종료할 수 있도록 정리합니다.
- 각 플랫폼의 상세 작업은 플랫폼에서 수행합니다. 포털은 인증·접근 제어, 신청·승인, API를 통한 필요한 정보 조회와 입력, 플랫폼 이동을 담당합니다. AI 학습, 데이터 분석, 클라우드 자원 실행 엔진을 포털에 새로 만들지 마세요.
- 공군·육군·해군·해병대 등 테넌트별 로고, 색상, 메뉴 순서와 표시, 사용자 권한, 플랫폼 접근권한을 분리합니다. 슈퍼유저는 테넌트 관리자를 지정할 수 있어야 합니다.
- 요구사항 식별자, 대응률, 발표용 설명은 사용자 화면·툴팁·샘플 제목에 노출하지 않습니다. 요구사항 추적은 소스의 내부 매핑과 문서에 유지합니다.
- 기존 K-RMF 전용 화면과 요구사항 대응/발표용 화면은 앞선 요청에서 비활성화되었습니다. 보존된 소스를 임의 삭제하거나 최신 사용자 요청 없이 다시 노출하지 마세요. 실제 감사 기능과 보안 통제는 계속 유지합니다.

## 4. 작업 A — 실제 인증과 플랫폼 진입

관련 범위: 로그인/로그아웃, 사용자·권한, 플랫폼 연동, 내 계정.

1. 기존 인증 구성을 조사해 사용할 IdP와 서버 신원 교환 경로를 하나로 확정합니다. OIDC Authorization Code + PKCE, 토큰 발급자·대상·서명·만료, 세션 회수와 로그아웃을 검증합니다.
2. 화면의 제로트러스트 안내와 실제 정책 판정을 연결합니다. MFA, 단말 상태, 접속망 등은 신뢰할 수 있는 공급자에서 받은 증거가 있을 때만 통과로 표시합니다. UI 체크박스나 일정 시간 대기로 인증 성공을 만들지 않습니다.
3. 네 플랫폼의 실제 URL, 허용 호스트, SSO 방식, 테넌트/역할 매핑을 계약으로 정의합니다. URL에 인증 토큰을 넣지 않습니다. 미설정 또는 권한 없는 플랫폼은 실행하지 않고 원인과 접근 신청 경로를 제공합니다.
4. 세션 만료, IdP 거부, 플랫폼 권한 거부, 주소 미설정, 연결 오류를 별도 상태로 처리합니다. 요청 시점에 서버가 권한을 다시 확인합니다.

완료 조건: 실제 IdP 시험 계정으로 로그인→허용 테넌트 선택→허용 플랫폼 SSO→로그아웃을 재현하고, 일반 사용자·다른 테넌트·회수된 역할·만료된 세션의 부정 시험이 통과해야 합니다. 데모 비밀번호/Guest/captureRole 조작은 운영 권한을 만들 수 없어야 합니다.

## 5. 작업 B — 테넌트 접근권한·관리자 지정·개인화 운영 검증

관련 범위: 사용자·정책·역할·메뉴, 내 계정, 환경설정, 테넌트 관리.

1. `20260924000001_platform_access.js` 및 기존 테넌트 설정 마이그레이션을 실제 배포 DB에 적용할 절차·롤백 계획을 검토합니다. 이미 구현된 플랫폼 정책과 개인 설정 저장 API를 재작성하지 말고, 배포된 버전과 실제 신원·테넌트 UUID 연결부터 확인하세요.
2. 테넌트의 플랫폼 허용 정책과 사용자/역할별 허용 정책의 서버 합성 및 launch 시 재검증을 실제 인증 사용자로 시험합니다. 테넌트가 닫은 플랫폼을 개인 설정으로 다시 열 수 없어야 합니다. 메뉴 숨김과 실제 업무 권한도 구별합니다.
3. 현재 `portal-admin` 슈퍼유저의 `branch-admin` 지정은 기존 `/v1/role-assignments`를 사용합니다. 이 경로와 지정 UI를 보존하고 전역 관리자라는 이유만으로 모든 테넌트 일반 업무 데이터에 무제한 접근하도록 RLS를 우회하지 않습니다.
4. 구현된 관리자 지정/회수의 유효기간, 변경 사유, 동시성, 마지막 관리자 보호, 감사 기록을 운영 IdP 사용자와 연결해 재검증합니다. 테넌트 관리자는 자기 테넌트와 위임받은 범위 안에서만 사용자·역할·플랫폼 접근을 관리합니다.
5. 플랫폼 순서·즐겨찾기의 `tenantId + userId` 저장과 다른 브라우저 복원을 확인합니다. 기본 테넌트 등 아직 브라우저에만 남는 추가 선호가 있다면 실제 제공 범위를 확인한 뒤 연결합니다. 군 공통 브랜드를 개인화가 바꾸지 않게 합니다.

완료 조건: 다른 사용자·다른 브라우저·새로고침에서 서버 설정이 재현되고, 테넌트 전환 시 이전 데이터가 노출되지 않아야 합니다. 해병대 포함 모든 등록 테넌트에 같은 동작을 적용합니다. 교차 테넌트 조회/변경, 자기 승격, 마지막 관리자 회수, 오래된 버전 저장은 서버에서 거부해야 합니다.

## 6. 작업 C — 개발 관리자 API 콘솔의 실제 연계

관련 범위: 플랫폼 연동과 각 플랫폼 담당자 협업.

1. `/developer-console` 및 `/platform-api-integration`의 같은 개발 관리자 화면, `docs/portal-experience/DEVELOPER_CONSOLE.md`, 기존 `API_CONTRACT_REGISTER.csv`를 출발점으로 사용합니다. 중복 콘솔을 만들지 마세요. 기존 담당 시스템·사용 화면·method/path·인증/보안·오류·협의사항 상세를 유지하고 확정된 계약 버전과 담당 팀을 연결합니다.
2. 샘플 계약 검증과 실제 접속 검증을 분리합니다. 계약 fixture 시험은 반복 가능하게 유지하되 외부 시스템이 실제 연결되었다고 표시하지 않습니다. API 목록과 화면 소비 지점을 문서와 함께 갱신합니다.
3. 실제 호출은 기존 서버 BFF의 `/v1/integrations/targets`, `/v1/integrations/test`를 확장합니다. 현재 `PORTAL_INTEGRATION_TARGETS`의 테넌트별 목적지와 서버 토큰 환경변수, GET 전용 경로를 사용합니다. 구현된 인가·감사·timeout·응답 크기 제한·비식별화·리다이렉트 차단을 보존하세요. 플랫폼용 secret은 서버 secret 저장소에서만 사용하고 브라우저 저장소·소스·로그에 넣지 않습니다.
4. 연결 대상은 환경별 allowlist로 제한합니다. 승인된 내부 플랫폼 주소는 명시적으로 등록할 수 있게 하되, 임의 URL/리다이렉트/DNS 변경으로 메타데이터 서비스나 미등록 호스트에 접근할 수 없게 검증합니다. timeout, 응답 크기 제한, 취소, 속도 제한, 민감 헤더·필드 마스킹을 적용합니다.
5. 구현된 요청 JSON과 샘플/실응답 구조의 초안 필수 필드·타입 검증을 보존하고, 플랫폼 담당자가 합의한 OpenAPI/JSON Schema로 교체합니다. 중첩 객체, 배열 항목, 상태 코드, 페이지네이션, 인증 위임, 파일·이벤트 계약을 확정하세요. HTTP 200 JSON 수신과 스키마 적합 판정을 계속 구별합니다. 쓰기 API 시험이 필요하면 테스트 환경·테스트 데이터·멱등성·복구 계약을 먼저 마련하며, 현재 GET 시험을 실운영 변경/삭제 실행으로 바꾸지 않습니다.
6. 현재 실호출 시도/결과는 서버 감사 원장에 요약 기록되고, 콘솔 요약 이력은 tenant+actor 브라우저 저장소에 최근 40건만 남습니다. 다중 브라우저에서 공유할 상세 테스트 이력의 서버 영속화·관리자 조회·보존 정책을 추가합니다. 토큰, 개인정보 및 요청/응답 원문은 저장하지 않습니다.

완료 조건: 독립 계약 시험 서버로 성공, 401/403, timeout, 잘못된 스키마, 취소, 재시도, 허용되지 않은 호스트, 권한 없는 사용자 시나리오를 자동 검증합니다. 실제 플랫폼의 staging 환경에서는 제공된 명세에 한해 별도 실증하고 검증 환경·계약 버전을 기록합니다.

## 7. 작업 D — 기존 업무 기능의 단계적 운영 전환

기존 화면과 데이터 모델을 유지하며 아래 순서로 연결하세요. 기능이 미완성이라는 이유로 탭·버튼·업무 흐름을 삭제하지 마세요. 외부 명세가 없으면 독립 계약 시험 서버와 포털 측 처리를 완성하고 외부 확인 항목만 분리합니다.

| 순서 | 범위 | 완료 조건 |
| --- | --- | --- |
| D1 | 프로젝트/워크스페이스 신청·승인·접속·종료 | 완성된 체험 신청 폼·검증·전체 입력 보존을 유지하고 서버 상태 전이, 멱등 신청, 동시 승인, 외부 작업 ID, 실패/보상 처리와 이력으로 연결. 실제 자원 생성은 플랫폼에서 수행 |
| D2 | 크레딧 신청·잔액·사용량·단가 | 원천 정산과 포털 신청 구분, 단위/집계 기준/확정 시각 명시, 원장·중복 차감 방지, 승인 권한과 감사 |
| D3 | 반입·반출 | 신청·승인·검사·전송의 상태 분리, 첨부 보관·해시·검사 결과·수신증, 실제 처리 확인 전 완료 표시 금지 |
| D4 | 카탈로그·검색 | 원천 자산 ID/version, 권한 필터와 페이지네이션, 색인 상태·지연·실패 표시, 접근 불가 자산의 자동완성/집계 누출 차단 |
| D5 | 게시판·내 계정·환경설정 | 완성된 제안 등록·수정·삭제·공감·댓글·검토 UI를 서버 다중 사용자 공유/권한·DB로 연결, 첨부 추가. 실제 프로필·세션/알림 API, API 키 일회성 노출·해시 보관·회수, 환경설정 저장·버전·감사 |

실증·데이터 준비 화면의 준비 상태 및 산출물 관리도 기존 범위에서 보존합니다. 실증 모델 학습이나 정확도 보장은 외부 플랫폼·수행 과제의 책임입니다.

- 앱 루트에서 `yarn tsc --noEmit`, 관련 프런트 테스트, 프런트/백엔드 빌드와 변경 파일 lint를 실행합니다. 실패가 나면 기존 실패인지 이번 변경인지 구분하고 해결합니다.
- `scripts/test-portal-runtime.mjs`를 실제 일회성 PostgreSQL/제한 런타임 계정으로 실행합니다. 운영 DB는 검증용으로 사용하지 않습니다.
- `scripts/test-tenant-portal-ui.mjs`와 이번 포털 경험 브라우저 검증을 최신 탐색 구조에 맞춰 실행합니다. 이전 스크립트가 사이드바와 API 콘솔 비활성 상태를 전제할 수 있으므로 현재 요청에 맞춰 회귀 기대값을 갱신합니다.
- 390/768/1440px에서 네 시안, 키보드 Tab/Enter/Escape, 앱 메뉴 열기·닫기·포커스 복귀, 플랫폼 이동, 내부 기능 진입, 로그인 실패, 테넌트 전환, 권한 거부를 확인합니다. 가로 넘침과 잘린 입력/버튼을 검사합니다.
