# 사용자 정의/제공 필요 항목 — KAIPotal 포털

> 작성일: 2026-09-24. 개발을 완성하기 위해 사용자(고객/운영 주체)가 결정하거나 제공해야 하는 항목을 정리한다.
> 각 항목은 "왜 필요한가 — 무엇을 정해줘야 하는가" 형태로 작성했다. 결정되면 관련 화면/배포 작업을 진행할 수 있다.

## 1. 메인 화면 시안 최종 확정 (우선순위: 높음)

- 현황: 메인 화면 디자인 시안 4종(Aurora / Focus / Orbit / Canvas)이 임시로 제공 중. 로그인 시 선택기가 노출된다.
- 정해줘야 할 것:
  - 최종 시안 1개 선택 (또는 시안별 수정 요구사항)
  - 선택 확정 시점 → 확정되면 `app.designReviewEnabled: false`로 선택기를 종료하고 기본 화면을 고정한다.

## 2. 인증 체계 (IdP) 연결 정보 (우선순위: 높음 — 작업 A 완성의 전제)

- 현황: 화면은 기관 OIDC 로그인 흐름을 준비했으나 실제 IdP 정보가 없어 데모(접근코드/게스트)로만 동작한다.
- 정해줘야 할 것:
  - 사용할 IdP 확정 (Keycloak 직접 구축 vs 기관 통합 인증 vs 기타)
  - OIDC 설정: issuer URL, realm, client-id, client-secret, redirect URI
  - MFA(다중인증) 적용 여부와 단말 상태/접속망 정책을 판정하는 시스템(EPP/NAC 등) 존재 여부
  - 세션 만료 정책, 로그아웃/세션 회수 요구사항
- 결정되면: 로그인 → 테넌트 선택 → 플랫폼 SSO → 로그아웃 전 구간을 실계정으로 검증한다.

## 3. 플랫폼(4개) 연결 정보 (우선순위: 높음)

- 현황: AI/데이터/클우드/VDI 카드와 앱 런처는 있으나 연결 주소가 미등록이면 "연결되지 않았습니다"로 안낸다.
- 정해줘야 할 것(플랫폼별):
  - 서비스 URL (HTTPS), SSO 방식(토큰 위임 vs 별도 로그인)
  - 테넌트(군)별 접근 정책 — 어느 군이 어느 플랫폼을 쓰는지 최종 목록
  - 플랫폼별 담당 팀과 협의 창구
- 포털 설정 방법: `/tenant-settings`의 플랫폼 관리에서 주소·사용 여부·역할 허용 범위를 등록하면 된다(관리자 화면 구현 완료).

## 4. 플랫폼 API 계약 (우선순위: 중간 — 개발자 콘솔 실연계의 전제)

- 현황: 개발자 콘솔(`/developer-console`)에 API 후보 40개(38+VDI 2)가 등록돼 있고, 서버 진단(테스트 어댑터)까지는 검증됐다. 실플랫폼 호출은 아직 없다.
- 정해줘야 할 것:
  - 각 API의 확정 명세(OpenAPI/JSON Schema) 또는 플랫폼 담당자와의 협의 일정
  - 인증 방식(토큰 발급 절차, 만료, 갱신)과 staging(시험) 환경 접속 정보
  - 쓰기 API(신청·승인 결과 회신 등)의 멱등성/복구 요구사항
  - 상세 테스트 이력의 보존 기간(현재 요약 이력만 서버에 남음)

## 5. 운영 DB 변경 승인 (우선순위: 높음 — 서버 저장 전환의 전제)

- 현황: 미적용 migration이 없다. 2026-09-24 배포에서 batch 3(`20260918000001_tenant_settings`, `20260924000001_platform_access`, `20260924000002_work_requests`)을 staging Cloud SQL에 적용했다. `20260916000003_audit_append_policy`는 36.3단계에서 이미 적용됐다.
- 배포 기록: `docs/FIREBASE_DEMO_DEPLOYMENT_LOG.md` 2026-09-24 항목
- 향후 migration이 추가되면: 적용 승인과 적용 시간대(재배포와 함께 진행) → staging Cloud SQL 적용(`run-portal-migrations.mjs`) → 백엔드 이미지 재빌드/배포 → 검증 순서로 진행한다. 각 migration은 되돌리기(rollback) 스크립트를 포함한다.

## 6. 업무 정책 값 (우선순위: 중간 — 목 데이터를 실제 값으로 교체)

- 정해줘야 할 것:
  - 크레딧: 단가표(GPU/CPU/스토리지 시간당 단가), 충전/차감 승인 권한자, 정산 주기
  - 반입·반출: 승인 권한자(역할), 검사 절차(악성코드/DLP) 담당, 보관 기간
  - 테넌트 쿼터: 군별 기본 쿼터와 변경 승인 흐름
  - 알림: 메일/쪽지 발송 수단(SMTP 게이트웨이 등)과 발신 정책
  - 작업환경(컨테이너) 생성: 승인 권한자, 기본 자원 상한
  - 공지사항/게시판 운영 주체와 등록 절차

## 7. 원본 RFP 문서 (우선순위: 높음 — 요구사항 검증의 전제)

- 현황: 저장소에 최종공고문 원본 PDF(`260723_제안요청서(안)_최종_v1.pdf`)가 없다. 기능분해 엑셀(`..._최신화_최종공고문기준_v7.24.xlsx`)만 근거로 쓰이고 있다.
- 정해줘야 할 것: 원본 PDF(및 확정 기능목록 엑셀)를 저장소 `proposal-package/` 또는 지정 위치에 제공.
- 이유: 원문 없이는 "전체 요구사항 충족"을 주장할 수 없고, 34단계(최종공고문 기준 최신화)의 정확한 반영 여부를 검증할 수 없다.

## 8. 운영 전환 우선순위 (우선순위: 중간)

- 현황: 제안 게시판·작업환경 신청·프로필·설정 등은 데모 모드(브라우저 저장소)로 동작한다. 다중 사용자 공유를 위해서는 서버 저장 전환이 필요하다.
- 정해줘야 할 것: 서버 저장으로 전환할 기능의 우선순위. 제안:
  1. 인증/권한 (반드시 최우선 — IdP 정보와 함께)
  2. 프로젝트/워크스페이스 신청·승인
  3. 크레딧
  4. 반입·반출
  5. 카탈로그·검색
  6. 게시판·내 계정·환경설정

## 9. 데모/접근 정책 (우선순위: 낮음)

- 정해줘야 할 것:
  - 접근코드(`ictway`)와 게스트 로그인의 운영 사용 여부 — 운영 전환 시 제거 대상인지
  - 시연(데모) 환경의 공개 기간과 접근코드 로테이션 주기
