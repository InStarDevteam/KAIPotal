# Kimi Code 개발 지시 — 국방지능형플랫폼 포털 최종 기능 완성

작성 기준: 2026-09-29. 아래 내용을 계획 제안이 아닌 실제 개발·검증 지시로 실행하라.

## 1. 목표와 이번 요청의 우선순위

기존 `kt-ai-portal` 프로젝트를 이어서 개발하여, 외부체계 없이 완성할 수 있는 포털 기능을 실사용 가능한 수준으로 구현하라. 기존 RFP 토의 결과, 화면 구조, 역할, 테넌트 경계와 미커밋 작업을 보존하면서 부족한 기능을 완성한다. 분석이나 일부 화면 수정으로 끝내지 말고 구현, DB 마이그레이션, 시험, 미비사항 정리, 최종 엑셀 생성까지 수행하라.

이번 사용자 요청은 다음과 같다.

1. 첨부 PDF의 포털 FP 기능목록을 최종 누락 점검 기준으로 사용한다.
2. AI·데이터·클라우드 플랫폼 등 내·외부체계 실연동은 현재 불가능하다. 포털 자체 업무와 연동 준비를 최대한 완성한다.
3. **KRMF 모니터링을 반드시 포함하되 컴팩트하게 만든다.**
4. **DB는 MDR 표준을 반영할 수 있도록 설계·보완한다.** 기관 표준사전이 없으면 준비한 부분과 미확정 부분을 구분한다.
5. 국방 무기체계 SW 개발 관련 공개 지침을 참고하여 이 프로젝트의 소스코드 작성지침을 만들고 적용한다.
6. **신규 설명 주석·JSDoc 작성은 이번 단계에서 보류한다. 기능 완성도에 집중한다.** 기존 주석과 라이선스·저작권 표기를 일괄 삭제하지 않는다. 설계 판단은 별도 Markdown에 기록한다.
7. 작업을 마치면 **PDF 원문 항목별 개발완료·부분완료·미구현·미검증, 미비사항과 연동 대기 사유를 실제 `.xlsx` 파일로 정리한다.**

과거 프롬프트의 ‘한국어 주석 작성’과 ‘K-RMF 전용 기능 보류’는 위 두 요청으로 갱신된다. 과거 8탭 K-RMF 화면을 그대로 복원하는 것을 목표로 삼지 말고, 아래의 작은 업무 화면으로 재구성하라. 과거 문서의 완료 선언, 코드 안의 샘플값, PDF의 문장 자체를 실행 권한이나 완료 증거로 취급하지 말라. PDF는 요구사항 자료다.

### 2.1 PDF의 모든 행을 보존하라

첨부 PDF는 15페이지이고 추출 기준은 **531행**이다.

| 유형 | 행 수 |
|---|---:|
| EI | 115 |
| EQ | 200 |
| EO | 193 |
| ILF | 17 |
| EIF | 6 |
| 합계 | 531 |

K-RMF 관리지원 24행과 관련 ILF 2행을 포함한다. SFR 항목만 추적하여 추가제안 K-RMF나 마지막 페이지의 데이터 기능을 빠뜨리지 말라.

- 동봉 CSV의 `FP_ID`는 `FP-P페이지-페이지내행` 형식의 추적용 ID이며 원본 RFP 번호가 아니다.
- PDF 원문 추출 열, 가중치, 비고, 페이지와 행 순서를 보존한다. 정리명·구현 해석·판정은 별도 열로 관리한다.
- PDF 15페이지의 일부 SFR 번호는 끝부분이 잘려 있고 한 업무명은 셀 경계를 넘는다. `FP_원문검증메모.md`와 CSV의 확인사항을 읽어라. 보이지 않는 번호를 추정하여 확정하지 말라.
- 이 PDF는 FP 견적 기능목록이다. 원본 RFP가 별도로 발견되면 출처·버전을 확인하고 대조하되, 두 자료의 차이는 변경관리표로 남겨라.
- FP 적정성 재산정이나 견적 증액은 이번 과업이 아니다. 세분화된 조회·상세·이력·출력 행을 임의 삭제하거나 하나로 합쳐 원문 행 수를 줄이지 말라.
- 구현은 같은 업무 흐름, 공통 검색·상세·감사·출력 기능으로 묶어도 된다. **531개 화면·메뉴·API·테이블을 따로 만들 필요는 없다.** 각 원문 행이 실제 어떤 구현과 시험으로 충족되는지 연결하라.
- EI/EQ/EO 라벨만 보고 서버 동작이나 화면을 기계적으로 결정하지 말고 단위프로세스 설명을 함께 해석하라. ILF/EIF 역시 물리 테이블 수가 아니다.

아래는 2026-09-29 소스 열람에서 확인한 출발점이다. 실행 시 최신 코드에서 재확인하라. 이 목록 자체는 시험 통과 선언이 아니다.

## 4. 실사용 기능의 공통 완료 기준

각 업무를 다음 경로로 끝까지 구현하라.

**입력·조회 화면 → 인증 → 서버 권한/소속 확인 → 입력·상태 검증 → 트랜잭션 저장 → 감사/알림 → 재조회 → 필요한 상세·이력·내보내기**

1. 운영 업무 상태는 PostgreSQL 또는 승인된 파일저장소에 저장한다. React state, localStorage, sessionStorage는 운영 원장이 아니다. 화면 선택·임시 UI 상태와 명시적 데모 fixture는 구분한다.
2. 서버에서 tenant/project/소유권/보안속성을 검증한다. 클라이언트의 role·tenantId를 신뢰하거나 숨긴 메뉴를 인가로 대신하지 않는다. 검색·건수·자동완성·첨부·다운로드에도 같은 범위를 적용한다.
3. 테넌트 전환 시 캐시와 진행 중 요청을 정리하고 오래된 응답이 새 테넌트 화면에 섞이지 않게 한다.
4. 생성·변경·취소·승인·반려·보완·종료 등 실제 업무에 필요한 상태와 허용 전이를 정의한다. 중복 제출·중복 승인·동시 수정에 멱등성, 버전 검사 또는 적절한 잠금을 적용한다.
5. 중요 업무 변경과 감사기록을 원자적으로 저장한다. 원격 호출을 긴 DB 트랜잭션 안에서 실행하지 않는다. 원격 실패는 업무 승인과 별도 처리 상태로 남긴다.
6. 목록에는 검색·조건 필터·정렬·페이지 처리, 상세에는 관계·이력·권한에 따른 동작을 제공한다. PDF가 요구하는 출력은 실제 해당 범위의 데이터·필터·시점을 반영한다.
7. 로딩·빈 데이터·입력 오류·권한 없음·충돌·통신 오류·연동 대기를 구분한다. 실패를 0건, 정상, 성공 토스트로 바꾸지 않는다.
8. 첨부는 실제 저장·버전·크기/형식 검사·다운로드 권한·만료/삭제 정책을 구현한다. 승인된 파일의 버전·해시와 다운로드 파일을 묶는다. 파일이 바뀌면 기존 반출 승인 효력이 자동으로 이전되지 않게 한다.
9. 비밀번호·토큰·비밀키·민감 본문은 로그와 엑셀에 기록하지 않는다. API 키는 원문 재조회 없이 생성 시 한 번만 노출하고 안전한 검증값·범위·만료·폐기를 관리한다.
10. 운영 인증은 검증된 IdP 신원과 서버 권한을 사용한다. 캡처 모드 역할 전환, guest, 미리보기 권한, 자동 mock fallback으로 운영 기능을 통과시키지 않는다.
11. 일정·금액·사용량은 서버 기준과 명시적 단위를 사용한다. 시각은 UTC 저장·한국시간 표시를 일관되게 하고, 크레딧 계산에는 정확한 decimal 및 반올림 규칙을 적용한다.
12. 공통 컴포넌트와 기존 디자인을 활용한다. 업무당 일관된 목록·상세·작성 흐름을 만들고 키보드 조작, 포커스, 읽을 수 있는 대비, 좁은 화면을 확인한다.

## 5. FP 영역별 구현 범위

아래는 원문을 대체하는 축약 목록이 아니다. **각 영역의 CSV 원문 행을 모두 확인하면서 구현할 체크포인트**다.

| 영역 | 이번에 완성할 포털 기능 및 경계 |
|---|---|
| 메인 포털 | 로그인 전후 이동, 사용자/소속/권한, 공지·신규 자산·지원·내 업무·상태 집계, 권한에 맞는 바로가기. 집계 원천·기준시각·부분 연동 상태 표시 |
| 로그인·인증 | 로컬 검증 가능한 IdP 로그인/로그아웃, 계정상태·기간·실패제한·유휴/최대 세션·세션 회수. 실제 SSO/MPKI/본인확인/메일은 어댑터와 미연동 상태 구분 |
| 사용자·외부사용자 | 등록 신청·검토·승인·반려·보완, 목록·상세·정보수정·공개설정, 소속·상태·기간·만료·권한 회수와 이력 |

### 놓치기 쉬운 세부 조건

- 브라우저 종료 이벤트는 전달되지 않을 수 있다. `beforeunload`만으로 즉시 로그아웃을 보장했다고 주장하지 말라. 서버 세션 만료·활동 감지·회수와 복원 시 재검증을 구현하고 원문 요구와 남는 차이를 기록한다.
- 비밀번호 복잡도나 세션 정책을 화면에 저장한 것으로 IdP 적용 완료 처리하지 말라. 로컬 IdP로 시험할 수 있는 부분을 구현하고 기관 SSO 적용은 별도 검증한다.
- 유사 명칭 검색과 의미 기반 검색을 구분한다. 포털 자체 데이터 검색을 먼저 완성하고, 의미 검색 엔진이 없으면 그 세부 요건을 미비사항에 명시한다.
- 크레딧 부족 시 포털의 추가 신청 제한은 구현할 수 있다. 실제 외부 자원 비활성화는 연결 전 ‘제어 대기’로 표시한다.
- 포털 승인 후 자원 생성, 외부 파일 반출, 외부 권한 적용은 각각 별도 실행 결과가 필요하다. 승인 완료만으로 ‘사용 가능’, ‘반출 완료’, ‘권한 적용 완료’로 전이하지 않는다.
- 기능별 저장소와 `/portal-work` 공통 신청함이 서로 다른 신청을 생성하지 않게 한다. 공통 원장을 재사용하고 유형별 확장으로 도메인 검증과 상세 정보를 보강한다.

### 6.3 데이터·권한·완료 기준

- 외부 보안체계가 없어도 포털의 기준선·증적·조치·변경·체크리스트 CRUD, 파일, 필터, 기한 계산, 집계, 출력은 실제 동작해야 한다.
- 기존 `krmf.view`, `krmf.evidence.submit`, `krmf.review`, `krmf.manage`를 서버에 연결하라. 수정·검토·조회·다운로드 권한을 구분하고 테넌트/프로젝트 범위를 확인한다. 감사관은 허용 범위 조회 중심이며 포털 관리자에게 보안 검토 권한을 자동 부여하지 않는다.
- 이행률은 분모·분자·제외 통제·기준시각을 정의한다. 통제가 없는 경우 ‘등록된 통제 없음’으로 표현하고 100% 정상으로 표시하지 않는다. 증적 업로드와 검토 완료를 구분한다.
- 증적 버전 변경, 조치 기한 경과, 정책/구성 변경 시 관련 통제와 다음 점검 대상에 반영한다. 동일 사유의 알림은 중복 발행을 막는다.
- 공식 K-RMF 통제 목록·기관 기준판이 없으면 import 가능한 구조와 별도 테스트 데이터를 준비한다. 실제 운영 화면의 공식 통제 코드·평가 결과를 임의 생성하지 않는다.
- 포털은 평가·인가 자료와 이력을 지원한다. 자동 인가 판정이나 기관 승인 대행 기능을 만들지 않는다. 사람이 입력한 인가 결과는 입력자·근거·출처·시각을 함께 남긴다.
- 이전 ‘K-RMF 메뉴가 없어야 함’ 테스트와 보류 문구를 이번 요구에 맞게 갱신한다. 단순 주석 해제, mock 통계, 안내만 하는 저장 버튼으로 완료 처리하지 않는다.

## 7. MDR를 반영한 DB 보완

### 7.1 적용 방식

MDR은 메타데이터 등록·표준화 요구로 다룬다. DB 제품이나 `fc_` 접두어만으로 준수가 결정되지 않는다. 적용 기관, 표준판, 표준단어/용어/도메인/코드 사전과 제출양식이 아직 없다면 이를 `기관 기준 미수령`으로 기록한다. **사전 부재 때문에 기능 구현을 중단하지 말고, 프로젝트 임시 정의와 기관 확정 정의를 분리하여 추후 매핑·변경할 수 있게 만든다.**

기존 PostgreSQL/Knex, 업무 DB 분리, `portal` 스키마와 `fc_` 관례를 먼저 활용하라. 기관 기준이 확인되지 않은 상태에서 대규모 이름 변경, ORM 교체 또는 OpenMetadata를 MDR의 대체물로 새로 구축하는 일을 선행조건으로 삼지 말라. Backstage 등 제품 내부 스키마를 임의로 바꾸지 않는다.

### 7.2 필수 산출물과 구현

`docs/final-completion/data/`에 다음을 생성하고 실제 migration/DB와 대조한다.

- `DATA_DICTIONARY.csv`: 엔티티/논리명/물리명/정의/표준용어ID/표준단어ID/도메인ID/자료형/길이·정밀도/단위/NULL/기본값/PK/FK/코드셋/보안·개인정보 구분/소유자/원천/보존정책/버전/매핑상태.
- `STANDARD_WORDS.csv`, `STANDARD_TERMS.csv`, `STANDARD_DOMAINS.csv`, `STANDARD_CODES.csv`: 표준단어의 한글명·영문명·약어와 용어의 구성 단어를 관리하고, 프로젝트 임시 항목과 기관 확정 항목을 명시적으로 구분. 제공되지 않은 공식 ID를 만들어 넣지 않는다.
- `MDR_MAPPING.csv`: 기관 원본 식별자·버전·출처와 현재 컬럼·코드 매핑, 불일치·예외·해결방안.
- `ERD.md`, `MIGRATION_PLAN.md`: 관계·소유권·외부 참조, 기존 데이터 영향, 정리/변환, 롤백 또는 전진 복구.
- 검증 스크립트: 등록 누락 컬럼, 표준단어·용어 참조 누락, 잘못된 코드/도메인, 자료형/길이 불일치, 중복 용어, 고아 참조, tenant 불일치를 검출. DB와 사전을 자동 비교하고 결과 파일 생성.

업무 모델에는 필요에 맞게 tenant/project/사용자 범위, 상태, 생성·수정 주체/시각, 버전, 출처를 갖추고 FK·유일성·CHECK·색인을 적용한다. 모든 테이블에 기계적으로 동일 컬럼을 강제하지는 않는다. 감사 원장·참조코드·외부 참조의 특성을 구분한다.

특히 프로젝트·멤버·신청·신청이력의 관계를 검사한다. 타 테넌트 객체 참조와 고아 레코드를 막고, 기존 데이터에 새 제약을 적용하기 전 오류를 보고·정리한다. RLS는 런타임 최소권한 계정으로 시험하고 연결 풀에서 컨텍스트가 누출되지 않게 한다. migration 계정과 runtime 계정을 분리한다.

빈 DB 초기화와 기존 DB 업그레이드를 모두 제공한다. 초기 운영 DB에 데모 사용자·K-RMF 통제·샘플 크레딧을 자동 주입하지 않는다. 기존 데이터 파괴나 운영 DB 직접 변경 없이 로컬 복제/시험 DB에서 검증하고 적용 스크립트를 준비한다.

MDR 대조가 끝나지 않은 상태를 ‘MDR 준수 완료’로 보고하지 말라. 데이터사전/검증기 구현 완료, 임시 매핑, 기관 사전 수령 대기를 각각 기록한다.

## 8. 외부체계 없이 완성할 연동 준비

외부 실연동 전체를 mock으로 대체하거나, ‘연동이 안 되므로 포털도 미구현’으로 남기는 두 경우를 피하라. 각 요구의 **포털 처리 범위와 외부 수행 범위**를 명시한다.

1. 기존 연동 레지스트리와 개발 콘솔을 조사한 뒤 내부 정규화 계약, provider adapter, 입력/응답 schema, 인증 방식·secret reference, timeout, 오류코드, 버전, 원천 식별자와 갱신시각을 정의한다.
2. 공식 외부 API 명세가 없으면 `내부 제안 계약`으로 표시한다. 가상의 endpoint와 callback 형식을 외부 합의 명세로 보고하지 않는다.
3. 테스트용 계약 서버는 운영 앱과 분리한다. 정상뿐 아니라 timeout·권한거부·오류 응답·부분 실패·중복/역순 이벤트·지연·재시도를 시험한다.
4. 요청의 접수·포털 승인·전송 대기·원천 처리 중·실제 성공/실패·취소를 구분한다. 사용자가 이해할 수 있는 한글 상태와 후속 행동을 제공한다.
5. outbox, worker/재처리, 멱등 키, 재시도 간격/상한, 처리중 lease, 실패 보관을 필요한 업무에 구현한다. 같은 요청/콜백이 여러 번 와도 이중 차감·이중 승인·중복 생성하지 않는다.
6. callback/webhook은 인증·서명·시간/재전송 검사·상태전이 검증을 적용한다. 제공자 기능이 확정되지 않은 부분은 계약 시험 범위로 기록한다.
7. 실제 운영의 미설정 원천은 `미연동/연동 대기/데이터 없음/수집 지연`으로 보여준다. 임의 실측치, 정상 배지, 성공 링크를 생성하지 않는다. 수동 등록을 허용한 데이터는 입력자·근거·원천을 표시한다.
8. 외부 URL과 진단 API는 서버의 허용 목적지/경로 및 SSRF 방어를 통과해야 한다. 내부 업무망 사용을 고려해 망별 허용 대역을 설정하되, 임의 URL·메타데이터 주소·우회 redirect를 허용하지 않는다.
9. 플랫폼 연결을 위한 어댑터·설정·오류 처리·계약 시험을 끝낸 항목은 ‘포털 연동 준비 완료, 실제 연동 대기’로 보고한다. 실제 외부 처리 성공과 구분한다.

로컬 PostgreSQL·IdP·파일저장소 등 포털 검증에 필요한 구성은 기존 `infra/local-integration`을 우선 확장한다. 기관의 AI 플랫폼, 실제 클라우드/CMP, MPKI, 메일/인사체계 자격정보가 필요한 부분만 의존성으로 남긴다. 사용자 요청 범위를 넘어 신규 대형 플랫폼이나 필수 Kubernetes 전환을 만들지 않는다.

## 9. 소스코드 작성지침을 만들고 적용하라

`docs/final-completion/CODING_GUIDELINES.md`를 간결하게 작성하고 실제 변경 코드에 적용하라. 아래 공식 공개 자료의 확인 가능한 판본·항목을 참고하되, 웹 포털에 적용한 프로젝트 규칙과 원문 규정 내용을 구분한다. 존재를 확인하지 못한 조항·문서번호·MDR 코드·적합성 인증을 만들어내지 말라.

참고자료 목록과 확인 범위는 동봉 `FP_원문검증메모.md`의 공식 출처 절을 따른다. 기관이 계약상 지정한 판본이나 별도 지침이 발견되면 비교하여 반영하라. 국방 무기체계 개발 매뉴얼의 요구사항 추적, 형상관리, 검토·시험·결함관리 관점을 현재 웹 기술에 맞게 적용한다. 무기체계의 C/C++ 코딩 규칙이나 모든 획득 산출물을 웹 포털에 그대로 강제하지 않는다.

최소 작성규칙:

- TypeScript 타입과 명시적 입력/출력 계약 사용. 외부 입력은 schema로 검증하고 근거 없는 `any`, non-null assertion, ts-ignore, lint 무력화를 추가하지 않기.
- UI, 도메인 서비스, repository, 외부 adapter의 책임 분리. UI 컴포넌트에서 DB/권한 규칙을 구현하지 않기.
- 의미 있는 명칭, 일관된 상태/오류코드/단위, 중복 로직 통합. 관계·권한·상태전이는 검증 가능한 작은 함수로 작성.
- 예외를 삼키거나 무조건 성공 반환하지 않기. 오류에는 요청 식별자를 제공하고 로그에는 민감정보를 제외.
- 파라미터화 쿼리, 서버 인가, XSS/CSRF 대응, 경로·파일·URL 검증, 업로드 제한, secret 외부화.
- 시간·재시도·동시성·멱등성을 명시하고 변경과 감사의 원자성 확보.
- 의존성/lockfile 일관성, 실제 사용하는 패키지 직접 선언, 라이선스 및 보안 취약점 확인. 무관한 전면 버전 업그레이드를 기능 개발에 끼워 넣지 않기.
- 요구사항 ID→구현→시험→결함→증적을 문서/데이터로 연결. 소스 전체에 추적 주석을 대량 삽입하지 않기.
- **이번 단계에서는 새 설명 주석·JSDoc을 쓰지 않는다.** 기존 법적 고지와 필요한 기존 주석을 보존하고, 함수·타입·테스트·별도 설계 기록으로 의도를 드러낸다. 주석 양이나 문서 분량을 개발 성과로 삼지 않는다.

## 10. 실행 순서와 검증

### 10.1 단계

1. **기준선 확정:** PDF/CSV 531행 검증, 현재 소스·변경사항·실행환경 조사, 각 행의 기능 그룹·UI/API/DB/연동 책임·수용기준·초기 상태 기록.
2. **공통 기반 보완:** 실제 인증/서버 인가·tenant/project 경계, 데이터 관계·migration, 공통 원장, 파일·알림·감사·오류 처리. MDR 사전을 병행한다.
3. **업무 완성:** 도메인별로 기존 UI를 API/DB에 연결하고 신청부터 결과 조회까지 완성. 실제 API가 있는 업무부터 데모 저장 경로를 교체한다.
4. **KRMF와 검색·연동 준비:** 위 6절의 작은 K-RMF 기능과 포털 검색, 외부 adapter·계약 시험·대기 상태를 완성한다. K-RMF가 마지막 미구현 항목으로 남지 않도록 독립 작업 단위로 관리한다.
5. **전체 회귀·운영 준비:** 역할별 실제 업무 시나리오, 데이터 보존, 보안 경계, 오류·동시성·재시작 시험과 로컬 설치/복구 확인.
6. **최종 보고:** 531행을 다시 대조하고 실제 `.xlsx`, 생성 스크립트, 증적·미비사항·외부 확인사항을 생성·검증한다.

단계 종료마다 `docs/final-completion/EXECUTION_STATUS.md`를 갱신하고 이어서 진행한다. 분석·계획·TODO 작성만 끝내고 멈추지 말라. 외부 사양 대기 때문에 막힌 기능은 준비 가능한 부분까지 끝낸 뒤 다음 독립 작업을 진행한다. 안전하게 확정할 수 없는 업무 규칙은 임시 규칙·영향·확인 필요 항목을 기록하고 보호적인 기본값을 사용한다.

### 10.2 실제 동작 시험

시험 데이터와 운영 데이터를 분리한다. 기존 통과 기록은 재실행 없이 이번 결과로 인용하지 않는다. 파일이나 테스트가 존재한다는 사실을 통과 증거로 삼지 않는다.

최소 시나리오:

- 일반사용자 신청 → 다른 승인권자 확인 → 승인/반려/보완 → 신청자 결과·이력·알림. 해당 유형마다 검증.
- 새로고침, 다른 브라우저/사용자, 서버 재시작 후 상태 유지. 데모 storage를 비워도 실제 데이터 유지.
- 같은 테넌트의 비참여자, 다른 테넌트 사용자, 조회 전용 감사관, 만료 사용자·회수 권한의 접근 차단. 직접 API·객체 ID 변경·파일 URL·검색·집계에도 적용.
- 중복 제출/승인·동시 수정·중복 사용량 이벤트, 감사 저장 실패와 외부 timeout 후 데이터 일관성.
- 첨부 업로드/재조회/다운로드, 승인 후 파일 교체, 무권한 다운로드와 만료 링크 차단.
- K-RMF 기준선 등록→증적 제출/검토→미흡 조치→기한 초과→변경 영향→필터·집계·내보내기 일치. 다른 tenant의 증적 차단.
- 크레딧 단가 변경 시 과거 내역 보존, 중복 차감 방지, 정정 이력, 미터링 없는 경우 미산출 표시.
- 외부체계 미설정/실패 상태에서도 포털 업무가 저장되고 가짜 정상 수치가 나타나지 않음.
- 빈 DB migration, 기존 DB 업그레이드, 반복 실행, 관계/코드/RLS/MDR 대조 및 복구 절차.
- 6역할·복수역할·복수테넌트, 테넌트 전환, 숨긴 메뉴, 기존 홈 시안, 390/768/1440px 등 주요 화면의 회귀.

`backstage-portal`에서 package scripts와 지원 Node/Yarn을 확인한 뒤 타입·린트·단위시험·빌드를 실행한다. 현재 명령 후보는 다음과 같다.

```sh
yarn tsc:full
yarn lint:all
yarn workspace backend test --watchAll=false
yarn workspace app test --watchAll=false
yarn build:all
```

프로젝트 루트의 실제 PostgreSQL 검사도 활용하라.

```sh
node scripts/test-portal-runtime.mjs
node scripts/test-portal-work-api.mjs
```

기존 `test-portal-shell.mjs`, `test-portal-experience-v2.mjs`, `test-tenant-portal-ui.mjs`, `test-developer-console-ui.mjs`는 회귀에 활용하되 데모/디자인 검증과 실제 운영 업무 검증을 구분한다. 기본 Backstage E2E 예제를 업무 E2E 통과로 집계하지 않는다. 새 업무는 실제 로그인·API·DB·파일을 사용하는 시험으로 증명한다.

시험 기록에는 case ID, 관련 FP ID, 실행일시, 환경, 코드 기준(commit과 미커밋 변경 식별), 명령, 기대값, 실제값, 결과, 증적 경로를 남긴다. `PASS/FAIL/BLOCKED/NOT_RUN/SKIPPED`를 구분하고 실패를 삭제하거나 미실행을 성공으로 집계하지 않는다. 계약 서버 성공은 기관 실연동 성공과 별도로 표시한다.

로컬 개발·검증과 배포 준비까지 수행한다. 기존 외부 서비스에 대한 재배포나 운영 DB 변경은 이번 프롬프트 자체의 요구가 아니므로 실행 완료와 배포 완료를 분리해 보고하라.

| 시험결과 | case ID, 관련 FP_ID, 환경/데이터, 기대/실제 결과, PASS/FAIL/BLOCKED/NOT_RUN/SKIPPED, 명령/일시/증적/이슈 |

### 11.2 개발점검표의 최소 컬럼

`FP_ID / PDF페이지 / 페이지내행 / 원문 어플리케이션 / 세부업무 / 단위프로세스 / 설명 / FP유형 / 원문가중치 / 원문비고 / 기능그룹ID / 포털수용기준 / 포털처리범위 / 외부수행범위 / 화면·동작 / API·서비스 / DB·원천 / 구현파일 / 포털개발판정 / 외부연동상태 / 시험상태 / 요구전체충족 / 시험ID / 증적경로 / 남은미비사항 / 차단사유·필요자료 / 우선순위 / 후속조치 / 판정일·환경·코드기준`

사용하지 않는 API·화면·DB 컬럼은 공란 대신 `해당없음`과 짧은 이유를 기록한다. ILF/EIF는 UI 유무로 판정하지 말고 데이터 구조·원천·관계·접근·갱신·이력과 검증을 근거로 판단한다.

### 11.3 판정 규칙

상태를 한 열에 뒤섞지 말고 아래처럼 나누어 기록한다.

- **포털개발판정:** `완료 / 부분완료 / 미구현 / 미검증`
  - 완료: 정의한 포털 범위의 저장·조회·인가·상태·이력·출력 등 해당 수용기준을 실제 시험으로 충족.
  - 부분완료: 구현된 경로가 있으나 필요한 동작/검증 중 일부가 부족하거나 결함이 남음.
  - 미구현: 실제 기능이 없음. 목업·안내 버튼·UI 껍데기만 있으면 해당 부분은 미구현.
  - 미검증: 코드가 있어도 환경/실행 증거 부족으로 동작 판정이 불가능.
- **외부연동상태:** `실연동 검증완료 / 연동준비 완료·실연동 대기 / 준비 미비 / 미검증 / 해당없음`
- **시험상태:** `PASS / FAIL / BLOCKED / NOT_RUN / SKIPPED`
- **요구전체충족:** `충족 / 일부충족 / 미충족 / 확인필요`. 요구에 포함된 외부 수행이나 공식 표준 검증이 남으면 포털 부분이 완료여도 전체 충족으로 표시하지 않는다.

원문에 반복된 상세/이력/출력은 동일 구현을 연결할 수 있다. 다만 연결한 기능이 **각 행이 요구하는 동작을 실제로 지원하는지** 별도로 판정하라. 그룹 하나를 완료 처리하여 모든 소속 행을 자동 완료로 복제하지 않는다.

적용 제외가 필요하면 원문 행을 남기고 근거·결정 상태를 기록한다. 확인되지 않은 제외 항목을 분모에서 빼 완료율을 올리지 않는다. 신규로 필요한 보완 작업은 별도 구현/이슈 ID로 추가하고 531행의 원문 ID를 재부여하지 않는다.

### 11.4 엑셀 품질 검증

- 한글이 정상 표시되고 Excel에서 열리는 유효한 `.xlsx`인지 다시 열어 확인한다.
- 원문 531행, 개발점검 531행, 고유 FP_ID 531개, 누락/중복 0건, K-RMF 관련 26행 일치 여부를 스크립트로 검증한다.
- 필터, 상단/식별열 고정, 줄바꿈, 적절한 열너비, 상태 드롭다운·조건부서식을 적용한다. 긴 설명을 잘라 저장하지 않는다.
- 완료행에 구현과 시험 증거가 있고, 미비행에 사유와 후속조치가 있는지 검증한다. 서로 충돌하는 상태를 검출한다.
- 요약 합계는 원문 FP_ID 기준으로 계산하여 다대다 매핑 때문에 중복 집계되지 않게 한다. 포털 완료율과 요구 전체충족률을 구분한다.
- FP 가중 합계는 원문 참고정보로 보존한다. 가중치나 테스트 개수로 실제 기능 완성도를 과장하지 않는다.
- 상대 증적 링크와 파일 경로의 존재를 검사한다. 비밀값·개인정보 원문·실제 토큰을 넣지 않는다. 사용자 입력 문자열이 수식으로 실행되지 않게 처리한다.
- 공식은 넣되 뷰어에 따라 값이 공란이 되는 문제를 확인하고, 사전 계산한 요약값과 집계 검증 결과도 제공한다.

## 12. 종료 시 보고 형식

마지막 답변은 한국어로 다음만 명확하게 요약하라.

1. 실제 완성한 주요 업무와 달라진 동작.
2. K-RMF 화면 위치·탭 수·지원 기능과 MDR 준비/미확정 상태.
3. 이번에 실행한 시험 결과와 실패·미실행·외부 차단 범위.
4. PDF 531행 기준 포털 완료/부분완료/미구현/미검증 건수 및 요구 전체충족 현황.
5. 남은 미비사항의 우선순위와 실제 연동에 필요한 자료.
6. 최종 엑셀·생성 스크립트·실행 가이드·검증 증적 경로.

준비된 환경에서 할 수 있는 구현과 수정은 끝까지 진행하라. 외부 연동 대기, 기관 표준 확인 대기, 운영 배포 여부를 정확하게 남기고, 성공하지 않은 기능을 완료로 포장하지 말라.
